# agents-orchestrator memory

Lessons that outlive a session. Newest first.

- 2026-11-01 (priority-double-delivery) priority sends are idempotent and wait out the wrapper's interrupt. `wrapper_interrupt_settle_seconds` (default 20) is rendered into every wrapper as `sessions.interrupt_settle_seconds`, and `Settings.priority_send_timeout_seconds` = send timeout + `priority_hold_seconds(settle)` = `3 * settle + 14` (two interrupts and the flushed-queue wait; four 1 s ESC spacings and two 5 s runner drains), 89 s by default; hooks are not counted. A priority send carries `message_id: orch-<id>`: the wrapper answers a repeat with the first send's turn (`duplicate: true`), and a 202 whose state is `pending` maps to Ambiguous (verifier decides). The verifier treats a matching record in state `pending` as in progress (`Answer.PENDING`: no change at any age, only the 600 s deadline applies), never as not-started. Why: the lanes live check (run 4) held a priority send 21 s in the wrapper, past the 15 s timeout; past the 60 s settle window the verifier would have requeued it and the re-send would have interrupted the first delivery. The settle window and the dispatching-stale validators are unchanged: the wrapper lists the turn from the request's arrival, and the send heartbeats the dispatching row. Rendering the new key changes every config hash, so the first deploy rolls agent pods.
- 2026-11-01 (s3-backup-restore, flat-name retention): flat-named archives (one object per group: `preset-<sha16>`, migrated keys) are age-deleted when older than the retention days, referenced by no live session's restore or save key, and past the grace period; keep-newest-K and the newest-of-group guard apply only to versioned groups (`<dir>/<now>`). Why: with 'never below 1' the dominant name shape never went stale-clean, defeating the cleanup goal. Cost: a fixed-name restore point idle for N days is deleted (sweep ships dry_run=true).
- 2026-11-01 (s3-backup-restore): the cache key became two Jinja templates, `restore_key` and `save_key` (surface `archive_name`), replacing `key` with no shim (migration 0015 copies a stored key into both). Why: a restore could not come from one name and a save go to another, so no restore-only mode, no history, no retention. Grammar refinement flagged to the user: `CACHE_KEY_RE` applies per path segment (1-4 segments, 200 chars, first segment never `sessions`, restore may end in one `/` for "latest under prefix") because the old whole-key rule forbids `/`. `now` is the lowercase stamp `20261031t120000z` (the plan said `...T...Z`, but uppercase breaks the segment rule). `restore_key`/`save_key` are `None` when unset (derived `preset-<sha16>` for both when both are None) and `""` when explicit (fresh start / restore-only); the model validator checks plain names only, `validate_spec` renders templates, because the sandbox is a child process and a stored spec is parsed on every read. Status records `restore_resolved` and `save_resolved` (full object keys), written with the running state before the Job exists, replacing `status.cache.key/object`.

- 2026-10-28, ingester re-attach after a wrapper resume (deploy-safe-agent-sessions D3, goal G1, amended the same day): root cause of the 20:07-20:29 hang. On SIGTERM the wrapper emits `session_closed`; the ingester stored it, marked the agent `dead` and ended the task. The reconciler then resumed the SAME wrapper session id, so `AgentRef` did not change and `refresh` never restarted the task; a re-attach would also have failed, because `_stored_closed` honoured any stored close. Fix: `agents.wrapper_resumed_at` (migration 0008, the next free number on main when the task ran) is the resume marker, written only by the reconciler through `set_wrapper_session(..., resumed=True)` on both resume paths (the stored session and `_pick`); an adopt or create writes NULL, and `clear_wrapper_session` clears it. `AgentRef` carries it, so a resume restarts the stream even after a close; it is a re-attach trigger only. A close is honoured only when the wrapper's live snapshot maps to `dead`: on attach, last stored non-gap event `session_closed` AND a dead snapshot; in the stream, a fresh `session_closed` is stored, not projected, and the snapshot is read: dead marks the agent dead and ends the task, live returns to re-attach from the close seq with the backoff reset. The first D3 rule, a close honoured unless the marker was later than its `events.created_at` (database order), failed on the incident path itself: with the ingester down across the shutdown and the resume, the fresh ingester streams from M < N, the wrapper replays the close N and stops there, and the close is stored (and was projected `dead`) after the marker, so every later attach honoured it. No timestamp or events.id choice fixes that, because the close is emitted before the resume but stored after it; a last seq in the marker would need a wrapper change (the snapshot carries none). Accepted risk: a session resumed and dead again while the ingester was down loses events N+1..k (never streamed); wrapper authority wins. The re-attach streams from `events.last_seq` (the wrapper continues seq across a resume, and a replay stops at a replayed close, so after the close's seq it reads the resumed events) and projects the snapshot, so a resumed `ready` becomes `idle` and notifies `agent_free` for the dispatcher. Replayed events at or below the last stored seq are never re-projected (unchanged `_store` rule), so a replayed, already stored close reads no snapshot.

- 2026-11-01 (superleader-crud O4): `render.env_entries` renders a session's own variables, sorted: protected as `secretKeyRef` (key `value`) to the Secret name in `sessions.secret_versions`, on the pod and on the init Job; plain with `expand=false` with every `$` doubled (the kubelet reads `$$` as `$`, so `$(VAR)` stays text), with `expand=true` as is. A protected variable with no snapshot entry raises at render rather than being dropped. In the wrapper config, `${NAME}` (also `${NAME:-d}`) is kept unescaped only in webhook `secret`/`headers` and MCP `env`/`headers` values and only when NAME is one of the session's env variables; `$$` stays an escape and every other reference (the platform's own tokens, text fields such as `system_append`) stays escaped, so a user cannot read `CLAUDE_CODE_OAUTH_TOKEN`. Session create snapshots the preset's live Secret names (`secret_store.snapshot_versions`, 422 `secret_unset` for a protected variable with no value, also for a create without a preset). GC versus create race: `snapshot_versions` takes the same per-(preset, name) advisory lock as `set_secret` and `sync_declared`, inside the create transaction, so a rotation or removal waits for the session row to commit and its collection then sees the reference. The api has one seam to the k8s secret store, `api/secret_store.py`, the only api module allowed to import `k8s` (the layering pin in `tests/test_api_sessions.py` was widened, as for `workspace.py`); the Kubernetes client is built on first use or passed to `create_app(kube=...)`. Chart: the api pod needs Secrets create/patch/delete in its Role (O11).
- 2026-11-01 (superleader-crud O5): requests take `SessionSpecIn` (env entries `EnvVarIn`: a protected one may carry a `SecretStr` value); `split()` returns the storable `SessionSpec` plus the values, so a spec object never holds one. Reads go through `secret_view` (`redact_spec_dict` for stored dicts, `redact_spec` for models), which rebuilds each protected entry as `{protected, expand, set, version, updated_at}` and copies nothing from the stored entry (a value that reached the DB by another route is still never shown). Presets take metadata from `preset_secrets`; a session's comes from its `secret_versions` snapshot (version parsed from the Secret name, `updated_at` = the session's `created_at`, because only the current version has a row). PUT order: validate, update the row, then write sent values and `sync_declared` (a failure after the row update returns 502 `secret_store_failed`, a retry of the PUT repeats it; the spec change is the first, validated side effect). Entries sent without a value are left alone (keep), dropped ones retire and are collected, flipping to `protected: false` needs a value by the model rule. Preset delete runs `sync_declared(..., [])` so the secrets are collected. The secret route is `PUT /api/v1/presets/{preset}/secrets/{name}` with `{preset}` an id or a name (plan text says name, existing routes say id); 1 MiB cap is 413 `secret_too_large`; a name that is not a protected variable of the preset is 422. The store is touched only when values were sent or rows exist, so a preset without protected variables never needs a Kubernetes client.
