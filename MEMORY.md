- 2026-10-29 (hive-decoupling D6, task orch-handover-outcome-note): a handover requester learns the outcome as a keyed `leadership_request` note, "handover request <id> applied: <pod> leads at epoch N" or "handover request <id> rejected: <reason>". `hive._read` selects, per hive session, the `kind = 'handover'` requests with a requester that are `applied` or `rejected` and `decided_at > now() - OUTCOME_WINDOW_SECONDS` (300 s, module constant, my call: long enough for the 10 s throttle and a few failed ticks, short enough that a restart re-sends little); `_push_outcomes` sends each to its `from_agent_id` only when that agent is not gone and has a wrapper session. The applied text uses the session's current leader row, not the request's `to_agent_id`, so it is true for an untargeted request and after a later change. Tracking is `HiveState.outcome_sent` (request ids per session, in memory, pruned to the ids still inside the window), not a column: the DB read already makes it work with any number of dispatchers, a restart re-sends each outcome at most once more, and a duplicate keyed note replaces itself in the wrapper inbox; a failed push is not remembered, so the next tick retries it. `Dispatcher._drain_leadership` now sets `_push_wake` after a pass for any session (it used to on a leader change only), because a rejection changes no leader and would otherwise wait for the timer; `leadership_pass` keeps its signature and the per-session 10 s throttle still applies. User requests have no requester and get no note. Fixes the plugin text claim that the outcome arrives as a hive-state note (the text itself is plugin-activity-tool's).

- 2026-10-28 (matrix-connector-agent-initi D2, D5, D12, task orch-chat-relay): the chat upstream relay. `api/chat.py` serves `GET /agent/v1/chat/rooms`, `POST /agent/v1/chat/messages`, `POST /agent/v1/chat/reactions` and `GET /agent/v1/chat/messages/{send_id}` on the agent port only and forwards each to `{ORCH_CHAT_URL}/chat/v1/...` after `require_agent`, the `session_send` leader check (`_leads`, 403 `not_leader`), the configured check (503 `chat_unconfigured`) and a 256 KiB body cap (413 `payload_too_large`). Why a relay: only the orchestrator can prove "session S's leader is calling" and only the connector knows the rooms, so the orchestrator vouches with its own `ORCH_CHAT_TOKEN` plus `X-Orch-Session` and `X-Orch-Slug` (slug from the sessions table) and the agent token never leaves it; nothing is stored, refusals stay synchronous. Why `chat`, not `matrix`: the orchestrator stays free of Matrix concepts and talks to one generic chat upstream contract (`/chat/v1`), so the connector behind it can change without an orchestrator change; there is one upstream, no channel registry (YAGNI). Upstream status and JSON body pass through byte for byte; a connection error, a 10 s timeout (`asyncio.timeout` over the whole call, not only httpx's per-phase timeouts) or a non-JSON answer is 503 `chat_unavailable` without the upstream text. The relay does not validate bodies (two validators would drift). The cap is 256 KiB because a valid maximal message escaped as JSON surrogate pairs is about 192000 bytes (interrogate Act 6). The `send_id` segment is percent-encoded with dots too, since httpx removes `.`/`..` segments and would otherwise walk the upstream path. Tests: `tests/test_agent_chat.py` (non-DB cases fake the three repository reads of `require_agent`/`_leads` so they run without Docker; `test_leader_only_and_identity_db` needs Postgres).

- 2026-10-28, rollouts (deploy-safe-agent-sessions D1, D2, goal G3): the agent StatefulSet renders `updateStrategy: {type: OnDelete}`, so the controller never replaces an agent pod; `reconciler/rollout.py:Replacer.step` (run by `_converge` after bootstrap, writing `status.rollout {revision, pending, waiting, leader_pending}`, dropped when nothing is pending) deletes at most one pod per session per tick whose `controller-revision-hash` differs from `status.updateRevision`. - 2026-10-28, ingester re-attach after a wrapper resume (deploy-safe-agent-sessions D3, goal G1, amended the same day): root cause of the 20:07-20:29 hang. On SIGTERM the wrapper emits `session_closed`; the ingester stored it, marked the agent `dead` and ended the task. The reconciler then resumed the SAME wrapper session id, so `AgentRef` did not change and `refresh` never restarted the task; a re-attach would also have failed, because `_stored_closed` honoured any stored close. Fix: `agents.wrapper_resumed_at` (migration 0008, the next free number on main when the task ran) is the resume marker, written only by the reconciler through `set_wrapper_session(..., resumed=True)` on both resume paths (the stored session and `_pick`); an adopt or create writes NULL, and `clear_wrapper_session` clears it. `AgentRef` carries it, so a resume restarts the stream even after a close; it is a re-attach trigger only. A close is honoured only when the wrapper's live snapshot maps to `dead`: on attach, last stored non-gap event `session_closed` AND a dead snapshot; in the stream, a fresh `session_closed` is stored, not projected, and the snapshot is read: dead marks the agent dead and ends the task, live returns to re-attach from the close seq with the backoff reset. The first D3 rule, a close honoured unless the marker was later than its `events.created_at` (database order), failed on the incident path itself: with the ingester down across the shutdown and the resume, the fresh ingester streams from M < N, the wrapper replays the close N and stops there, and the close is stored (and was projected `dead`) after the marker, so every later attach honoured it. No timestamp or events.id choice fixes that, because the close is emitted before the resume but stored after it; a last seq in the marker would need a wrapper change (the snapshot carries none). Accepted risk: a session resumed and dead again while the ingester was down loses events N+1..k (never streamed); wrapper authority wins. The re-attach streams from `events.last_seq` (the wrapper continues seq across a resume, and a replay stops at a replayed close, so after the close's seq it reads the resumed events) and projects the snapshot, so a resumed `ready` becomes `idle` and notifies `agent_free` for the dispatcher. Replayed events at or below the last stored seq are never re-projected (unchanged `_store` rule), so a replayed, already stored close reads no snapshot.

- 2026-10-27, file download relay (file-download-in-file-browse D4): `GET /api/v1/sessions/{id}/files/download` is the first route that streams bytes from a wrapper instead of relaying JSON. `WrapperClient.open_download` sends the streamed GET and the route maps its status through `_wrapper_errors` (the one map `forward` also uses) before building the response, because once `http.response.start` is sent the status is fixed: a refusal decided after it could only be a broken download, never a JSON error. Not on the service-port allowlist: no in-cluster service needs file downloads, as for the other file routes.
